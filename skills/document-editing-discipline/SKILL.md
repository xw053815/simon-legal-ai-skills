## 0. 定位

本技能不是排版建议，是排版**铁律**。所有对外交付的 `.docx` 必须逐项通过。

**P0 铁律**：对外正式交付的客户版 Word 文档，表格中禁止使用 ✅❌ 等非文字符号，统一使用文字表述（如"是/否""需公证认证/无需公证认证"）。这些符号在客户眼中属于不专业的表现。

## 1. 核心原则

### 1.1 文书类型识别（三轨分类矩阵 · v7.0）

**第一判断永远是轨道**：先定文档属 A/B/C 哪一轨，轨道决定颜色体系与参数包，再从参数包取完整排版规格（§2.16）。**禁止逐项现场决策**——输出不稳定的根因就是"多选项靠判断"，三轨制消除判断。

| 轨道 | 文档类型 | 颜色 | 字体方案 | 编号体系 | 模板 |
|------|---------|------|---------|---------|------|
| **A 轨·诉讼** | 起诉状/答辩状/上诉状/再审申请书、代理词/辩护词、证据目录、诉讼类申请书（保全/执行/调查令）、庭审提纲 | **单一色调（黑白）** | 法院版：正文仿宋+标题宋体加粗（方案B）；客户版诉讼文件：正文宋体+标题黑体（方案A） | 诉讼编号（一、（一）） | 诉讼模板 |
| **B 轨·非诉严肃** | 律师函、法律意见书（正式出具） | **黑白**（允许律所信头） | 方案A | 非诉编号（1. 1.1） | 律师函/意见书模板 |
| **C 轨·非诉商务** | **法律备忘录（Memo）/法律分析报告/服务方案/报价函/尽调报告/商务汇报** | **藏蓝 #1A3A5C 强调色（默认强制）** | 方案A + 招股书标题字号（§2.2B） | 非诉编号（1. 1.1） | Memo/报告/商务模板 |

**边界规则（防止误判）**：
1. **律师函、法律意见书属 B 轨**——严肃信函，禁止强调色（用户明确口径）
2. **法律备忘录、法律分析报告、服务方案属 C 轨**——商务产品，**默认强制**藏蓝强调色，不需要客户要求才启用
3. **诉讼文件的客户版**（如发给客户看的起诉状草稿）仍属 A 轨，保持黑白——轨道由"文件性质"决定，不由"受众"决定
4. **客户明确要求的格式要求 > 三轨参数包**——客户书面/明确指示（如"要黑白""用我们 VI 色"）优先于本规范，须在交付记录注明偏离项
5. **混合类型文档按主导文书类型定轨**——附件独立成篇的可独立定轨
6. 不确定 → 按 C 轨（商务文件默认带强调色）

### 1.2 受众分级与字体方案

| 方案 | 适用场景 | 标题中文 | 正文中文 | 英文/数字 |
|------|---------|---------|---------|----------|
| **方案A：客户版商务** | 所有向客户交付的正式文书 | **黑体** | **宋体** | Times New Roman |
| **方案B：法院版诉讼** | 提交法院/仲裁庭的诉讼文书 | **宋体** | **仿宋** | Times New Roman |

选择规则：
- 给客户看的 → **方案A**（黑体标题 + 宋体正文 + TNR）
- 提交法院的 → **方案B**（宋体标题 + 仿宋正文 + TNR）
- 不确定时 → 方案A

### 1.3 四阶段任务流程

```
E · Explore（识别文书类型 + 确定级别）
    │  识别文书类型 → 确定编号体系 + 模板
    │  识别受众/正式等级 → 确定字体+字号+页边距方案
    │  输出：文书类型卡片 + 排版参数表
    ▼
P · Plan（选定模板 + 排版参数）
    │  选定模板 → 选定字体方案 → 选定排版参数 → 选定额外需求
    ▼
I · Implement（执行排版 + 套用模板）
    │  OfficeCLI 构建基础排版 → 注入内容 → 保存
    ▼
V · Verify（独立审校 + 字体验收）
    │  双引擎交叉核验 → 审校清单逐项通过 → 交付
```

**排版者 ≠ 审校者**：V 阶段必须由不同 Agent/模型/视角执行，禁止同一 Agent 执行又审查。

### 2.2A 藏蓝强调色规范（C 轨强制 · v7.0 重写，替代旧商务蓝可选规范）

**适用**：C 轨非诉商务文件（法律备忘录/法律分析报告/服务方案/尽调报告）——**默认强制启用，无需客户要求**。A 轨诉讼、B 轨严肃信函一律黑白，禁止启用。

**色板（唯一权威）**：

| 角色 | 色值 | 用途 |
|------|------|------|
| 主色藏蓝 | `#1A3A5C` | 一级标题文字、表头文字（加粗）、页眉 0.5pt 分隔线 |
| 表头底浅藏蓝 | `#E8ECF2` | 表格表头底纹（默认样式，唯一） |
| 斑马纹 | `#F5F7FA` | **默认不使用**；仅客户明确要求时启用 |

**使用约束（违反即不合格）**：
1. **强调色仅限三类元素**：一级标题文字 + 表格表头 + 页眉分隔线——按元素枚举替代面积估算，出现第四类即超标；**正文 100% 黑色**
2. **表头唯一样式**：浅藏蓝底 `#E8ECF2` + 藏蓝字加粗（固定默认，无"或"）；客户明确要求深蓝底白字时才启用备选
3. 表格边框、页眉页脚文字、**页码保持黑色**；二级及以下标题用黑色加粗（仅一级标题用藏蓝，保证克制）
4. **无彩打印降级**：需打印/传真时，强调色统一降级为"黑色 + 加粗/下划线"，不留彩色
5. **officecli 语法（v7.0 实测修正，2026-08-20）**：run 文字色 `"color":"1A3A5C"`；单元格底纹 `"shading":"E8ECF2"`；页眉段落底边框线分两步——先 `"pBdr.bottom":"single"`（officecli 的 pBdr 仅接受样式枚举，**不支持** `"single,1A3A5C"` 复合值），再用 `raw-set` 补色：`officecli raw-set <file> /header[1] --xpath "//*[local-name()='pBdr']/*[local-name()='bottom']" --action setattr --xml "color=1A3A5C"`

> 旧 v6.5 商务蓝三件套（#1F4E79/#DEE7F1/#F4F7FB）已废弃，仅保留变更日志说明。

### 2.2B 金融级排版参考（招股书规范 · C 轨适用）

来源：证监会及上交所、深交所关于申请文件/招股说明书格式准则（正文宋体小四、1.5 倍行距；一级标题黑体三号、二级黑体四号、三级黑体小四；各级标题段落间距一致；表格不小于小五 9pt）。**适用于 C 轨非诉商务文件**（与方案A 兼容；标题字号与藏蓝强调色叠加使用时，藏蓝仅用于一级标题文字）：

| 元素 | 规范 |
|------|------|
| 正文 | 宋体小四 12pt，1.5 倍行距 |
| 一级标题 | 黑体三号 16pt |
| 二级标题 | 黑体四号 14pt |
| 三级标题 | 黑体小四 12pt |
| 标题段落间距 | 各级标题分别采用一致的段落间距（示例：一级段前 14pt 段后 8pt，二级段前 8pt 段后 4pt） |
| 表格 | 内容不小于小五 9pt（客户版建议表头 10.5pt、表体 10pt） |
| 章节分隔 | 章与章、节与节之间有明显分隔标识 |

### 2.3 标题层级

```
诉讼文书（红圈所四级体系）：
  一级：一、二、三、……（宋体加粗，顶格）
  二级：（一）（二）（三）……（仿宋加粗，缩进 2 字符）
  三级：1. 2. 3.……（可缩进，与上级对齐）
  四级：（1）（2）（3）……（缩进 2 字符）

非诉文书（Memo/报告/意见书）：
  一级：1. 2. 3.……（宋体加粗，顶格）
  二级：1.1 2.1 3.1……（仿宋加粗，缩进 2 字符）
  （如内容分级过多，可延伸三级 1.1.1，保持与上级编号对齐）
```

**原则（红圈所标准）**：
1. 标题层级最多四级，**严禁层级跳跃**（不得直接从一级跳到三级）。
2. 内容确需三级以上表达时，优先用"段落内分号并列"或"首句加粗法"保持版面克制。
3. **标题不带句号**；各级标题末标点统一（"1."后为点号，不可用顿号）。
4. 阿拉伯数字编号后统一使用半角点号（"1."），不可用顿号（"1、"）。
5. 整段左对齐，次级别标题适当缩进，版面清晰。

> **默认两级**（大多数文书够用）；仅当内容结构确实需要时扩展到四级，宁少勿滥。

### 2.4 段落与行距

| 项目 | 标准 | 依据 |
|------|------|------|
| 对齐 | **两端对齐**（含标题和正文） | 红圈所+律协通用 |
| 首行缩进 | **2 字符**（全文无例外，即首行左空两字、回行顶格） | 红圈所标准 |
| 行距 | **A 轨法院版（方案B）：固定值 28 磅**（唯一值）；**B/C 轨及 A 轨客户版（方案A）：1.5 倍行距**（唯一值）。v7.0 起无"或"选项，禁止现场选择 | 红圈所标准 |
| 段前/段后 | **均设为 0**（靠行距控制，不靠空行）；段落间如需分隔用段后间距 | 红圈所标准 |
| 段落长度 | 每段 **5-7 行**，过长则拆分 | 知乎实务 |

> **绝对禁止手动敲空行**。Word 中连续两个段落标记（¶¶）= 排版不合格。正文与标题、正文与落款之间如需空一行，用段前/段后间距实现，不得手动回车空行。

### 2.5 编号体系

| 文书类型 | 编号格式 | 规则 |
|---------|---------|------|
| 诉讼文书 | 一、→（一）→ 1. →（1） | "一"后加顿号；"（一）""（1）"后不加顿号；"1."后为半角点号 |
| 非诉文书 | 1. → 1.1 | "."后加半角空格 |

> **红圈所编号标点规则（v6.1）**：阿拉伯数字编号后统一使用半角点号（"1."），不可用顿号（"1、"）；标题不带句号。

### 2.6 页码（v7.0：红圈所书刊式）

| 参数 | 标准 |
|------|------|
| 位置 | **页脚书刊式：单页码居右空一字、双页码居左空一字**（红圈所标准，替代旧"底部居中"） |
| 格式 | **左右一字线：— 1 —**（半角阿拉伯数字，两侧各一条一字线） |
| 字体 | **Times New Roman 10.5pt**（页码为数字，按字体铁律统一 TNR；页脚保留 2.8cm 边距） |
| 可选格式 | 客户版商务文件如需总页数，可附加 `1 / X`（PAGE/NUMPAGES 域），但**书刊式单右双左为默认** |
| 短文档 | **≤2 页不加页码** |
| 封面/目录 | 不计入页码（分节，正文从第 1 页起） |
| 附件 | 独立编页码，从第 1 页起 |
| 签字页 | 无页码，页脚写"《XX》之签字页" |
| Word 实现 | 域代码 `PAGE`（分节下双页左/单页右，靠奇偶页不同页脚实现） |

### 2.7 页眉

| 文件类型 | 页眉内容 | 字体 |
|---------|---------|------|
| 对外正式 | `[律师事务所名称]`（左）+ `YYYY 年 M 月 D 日`（右） | 见 §2.2（统一小五 9pt） |
| 律师函 | 律所信头 + 日期 + 档案编号 | 见 §2.2（小五 9pt） |
| 内部讨论稿 | `DRAFT — 内部讨论稿 — 不得对外引用` | 宋体 小五 9pt，红色 |
| 客户机密 | `客户机密 — 仅限授权人员查阅` | 宋体 小五 9pt |

### 2.8 标点符号

| 规则 | 说明 |
|------|------|
| 中文内容 → 全角标点 | ， 。 ； ： ！ ？ "" '' 《》 |
| 英文内容 → 半角标点 | , . ; : ! ? "" '' |
| 法律文书→禁感叹号 | 陈述事实用句号，并列陈述用分号 |
| 中英混排标点不混用 | 中文段落中的英文不改变全文标点体制 |
| 标点与字体一致（红圈所标准） | **中文标点跟随中文字体**，**西文标点跟随西文字体**（TNR） |

> **双引号铁律（P0）**：中文段落中**必须使用全角双引号**（U+201C/U+201D），绝对禁止使用直双引号（U+0022）。
>
> **括号规范（分场景，2026-08-04 用户确认）**：中文说明文字用**全角括号（）**（如"（以下简称'委托人'）"）；纯英文内容或编号引用用**半角括号()**（如"(see Exhibit A)"）。禁止同一篇文书内中文括号半角/全角混用。

## 4. 修订模式与版本管理

### 4.1 修订模式（Track Changes）

### 4.1.1 触发条件

用户要求修订/留痕/Track Changes/修改痕迹/修订痕迹/修订稿/修订版时，必须启用本模块。**凡涉及已有文档的任何修改——添加、删除、替换、格式调整（字体/加粗/颜色/对齐/间距等）——一律以原生修订标记呈现，禁止"改了不留痕"**（v7.1 强化）。

### 4.1.2 工具路径选型（v7.1 重写：OfficeCLI 原生修订首选）

| 路径 | 工具 | 适用场景 | 支持能力 | 优先级 |
|------|------|---------|---------|--------|
| **OfficeCLI** | officecli v1.0.143 `set` 修订语法 | 一切修订任务（默认首选） | **已实测**：ins/del/format（rPrChange）+ `revision.author` + `query` 核验 + accept/reject；**官方支持未实测**：moveTo/moveFrom（需用时先最小实测再使用） | **首选** |
| python-docx 原生 | `apply_revisions.py` / `preserve_format_revisions.py` | 无 OfficeCLI 环境；复杂跨 run 修订 | ins/del + run 级格式继承 | 降级备选 |
| docx-editor / docs-comment-mcp | — | **废弃**（v7.1 起不再使用） | 格式漂移风险高 | 不推荐 |

**核心原则（v7.1 强制）**：
1. **全类型留痕**：添加（ins）/删除（del）/**格式调整（format→w:rPrChange / w:pPrChange）** 都必须以 Word/WPS 原生修订标记呈现，右侧可逐条接受/拒绝；禁止直接覆盖原文后靠批注或颜色伪装。移动留痕（moveTo/moveFrom）官方支持但未实测，需用时先最小实测再使用
2. **author 统一"律师"**：所有修订的 `revision.author=律师`，禁止出现 WorkBuddy/AI/个人名
3. **同文件单引擎铁律**：OfficeCLI 与 python-docx 不得混用修改同一文件（修订生成与格式修复用同一引擎）

**实测语法（officecli v1.0.143，2026-08-20 验证通过）**：

```bash
# 替换留痕（自动生成 del 旧 + ins 新 一对修订）
officecli set 文件.docx /body --prop find=旧词 --prop replace=新词 --prop revision.author=律师
# 删除留痕（纯删除）
officecli set 文件.docx /body --prop find=删除词 --prop replace= --prop revision.author=律师
# 格式调整留痕（生成 format 修订 rPrChange）
officecli set 文件.docx /body --prop find=目标词 --prop bold=true --prop revision.author=律师
# 核验修订 author 是否全部为"律师"（V 阶段强制）
officecli query 文件.docx "revision[@author!='律师']"
# 接受/拒绝全部修订（须先审查，禁止无脑 Accept All）
officecli set 文件.docx /revision --prop revision.action=accept
```

**匹配语义（v7.1 补充）**：`--prop find=` 的匹配语义（全局/首个）以实测为准；**多处同名仅需改一处时**，先用 `query`/`view` 定位目标所在段落，再限定路径操作——`set 文件.docx /body/p[N] --prop find=旧词 --prop replace=新词 --prop revision.author=律师`（段落级定位，避免误伤其他同名处）。

**完整操作指南和代码示例**：见 `references/revision-mode-guide.md`

### 4.1.3 作者与时间戳（v7.1 收紧）

| 项目 | 规范 |
|------|------|
| 作者名 | **统一 `"律师"`**（v7.1 起唯一值），禁止显示为 `"WorkBuddy"`/`"AI Assistant"`/个人姓名 |
| 时间戳 | 默认当前时间；如需特定时间，用 ISO 8601 格式（禁止硬编码过期时间） |
| 校验 | V 阶段执行 `query revision[@author!='律师']`，有命中即失败 |

### 4.1.4 操作前必须备份

**任何修订操作前，必须备份原始文档。** 禁止在原文件上直接生成修订（除非用户明确说"覆盖原文件"）。

### 4.1.5 格式修订留痕规范（v7.1 新增 · 调格式也必须留痕）

**原则**：格式调整（字体/字号/加粗/颜色/对齐/行距/缩进等）同样是"修改"，必须以原生修订标记呈现——Word 用 `<w:rPrChange>`（run 属性修订）/ `<w:pPrChange>`（段落属性修订），WPS 同构。

**实现**：
- **首选 OfficeCLI**：`officecli set 文件.docx /body --prop find=目标词 --prop bold=true --prop revision.author=律师` → 自动生成 format 修订（rPrChange），修订前格式快照保留在 rPrChange 内
- 段落级格式（对齐/行距/缩进 → pPrChange）：`officecli set 文件.docx /body/p[N] --prop align=both --prop revision.author=律师`
- **降级 python-docx**：手工构造 `<w:rPrChange w:id w:author="律师" w:date>`（修订前完整 rPr 快照嵌入），见 `revision-mode-guide.md`

**禁止**：禁止直接 set 格式后不留修订（覆盖式改格式 = 改了不留痕 = 违规）。

### 4.1.6 拟人化修订纪律（v7.1 新增 · 像律师手工修订）

1. **最小精确编辑**：只标记实际变化的文本——改 "30 天"→"60 天"，只标记 `30`→`60`，**禁止把整句/整段塞进修订标记**（律师手工改不会整段划掉重写）
2. **逐处留痕**：一次多处修改时每处独立标记（多处同性质修改不合并），保持每处可单独接受/拒绝
3. **嵌套修订统一口径（v7.1 修订）**：**禁止生成嵌套修订**（在他人 `<w:ins>` 内再生成新修订会导致 WPS/Word 显示异常、接受/拒绝行为不可控，且降级脚本不支持）。目标文本已在他人插入内容内时：将修订放置于外层 `<w:ins>` **之外**（紧邻前后），author 保持"律师"，并在交付说明中标注该处为"修订他人插入内容，请人工复核"
4. **双向验证**：修订完成后必须验证——接受全部修订后内容符合预期 + 拒绝全部修订后还原原文（任一项失败 = 修订不完整）
5. **禁止无脑 Accept All**：接受/拒绝必须逐条审查后执行（法律文书不接受未经审查的批量接受）

## 5. 语言与表达

### 5.1 三问过滤器（强制，每句话都必须过）

1. **这句话在红圈所的真实法律备忘录里出现过吗？** 没出现过 → 删掉重写
2. **这句话去掉后，核心意思还在吗？** 在 → 删掉
3. **换成"本所认为/本所建议/本所兹"结构，意思一样吗？** 一样 → 换

### 5.2 红圈所标准措辞

| 场景 | AI味（禁止） | 红圈所标准（使用） |
|------|-------------|------------------|
| 开头 | `我们建议……` | `本所建议……` |
| 分析 | `我们认为……` | `本所认为……` |
| 引出 | `值得注意的是……` | 直接陈述，不加引导语 |
| 过渡 | `综上，……` | `本所认为，……` |
| 结论 | `综上所述，……` | `鉴于此，本所认为……` |
| 引用 | `根据《XX法》` | `《XX法》第X条规定……` |
| 委托 | `受……委托` | `本所接受……委托` |

### 5.3 禁止使用的 AI 味词汇

```
结论先行、综上、综上所述、总而言之、毋庸置疑、
值得注意的是、需要指出的是、需要强调的是、显而易见、
众所周知、不难看出、不难发现、不难理解、
首先、其次、再次、最后（超过3层时）、
在……方面、从……角度、基于……考量、考虑到……因素、
换言之、也就是说、具体而言、进一步而言、
我们建议、我们推荐、我认为、我们相信
```

### 5.4 章节标题标准名称

| 章节 | 标准名称 | 禁止使用的名称 |
|------|---------|---------------|
| 第一章 | 执行摘要（Executive Summary） | 结论先行、核心结论、摘要 |


## 6. OfficeCLI 执行层

### 6.1 环境与工具激活

- **二进制**：`[用户目录]\AppData\Local\OfficeCLI\officecli.exe`（v1.0.143）
- **文档**：`officecli help <command>` 查看帮助
- **核心命令**：`create` / `add` / `set` / `remove` / `get` / `batch` / `save` / `validate` / `view` / `raw` / `merge`

### 6.2 首次最小验证门禁

**任何新建文档任务，必须先跑最小测试（≤5 条指令）验证 props 语法**，确认 `font.ea`/`size`/`bold`/`firstLineChars`/`lineSpacing` 等核心 props 语法正确后，再生成完整 batch。**禁止跳过最小验证直接生成 100+ 条指令的 batch**——原子回滚机制下，任何单条失败将导致全部指令不生效。

**⚠️ 最小验证与正式构建必须用不同文档（2026-08-04 实测教训）**：最小验证若跑在正式目标文档上，其段落已占用 `/body/p[1]-p[N]`；正式 batch 的 run 追加索引（`/body/p[para_idx]`）若从 1 重新计数，会导致 run 追加错位（混合加粗文本被拼接到错误段落）。正确做法：
- 最小验证 → 独立临时文件（如 `_tmp_min.docx`），验证后删除
- 正式构建 → 全新 `create` 的文档
- 若确需在同一文档上分步构建，batch 生成时必须计算既有段落偏移（正式段落索引 = 既有段落数 + 本地计数）

### 6.3 交付门禁（Delivery Gate）

任何失败 = 不交付。必须全部通过：
1. `officecli validate` → 无架构错误
2. `officecli view issues` → 无 overflow/format/structure 问题
3. `officecli view text` → 无残留占位符
4. 双引擎交叉核验（见 §6.4）→ 无格式偏差

### 6.4 双引擎交叉核验

**核心原则**：OfficeCLI 负责"造"，python-docx 负责"验"。不在同一文件上混用两种引擎修改，但审查时用另一引擎只读检查是完全合规的。

| 引擎 | 检查项 |
|------|--------|
| OfficeCLI（结构层） | `validate` → 无架构错误；`view issues` → 无结构问题 |
| python-docx（格式层） | 四层字体覆盖率 100%；OOXML 行距/页边距/首行缩进/字号正确 |

**审查脚本**：`references/audit_docx.py`

**禁止事项**：
1. 禁止在审查时修改文件（python-docx 审查脚本只读不写）
2. 禁止跳过任何一方（OfficeCLI validate 通过不代表排版正确）
3. 禁止将审查脚本的输出作为最终交付物

### 6.5 Markdown 中间层

**适用场景**：固定格式/B 级文书（身份证明书/授权委托书/律师函）；模板化批量生成；客户版/法院版格式分离。

**不适用场景**：高度定制化文书（起诉状/代理词）；修订痕迹模式（Track Changes）。

**工作流**：Markdown 内容文件 → JSON 数据文件 → 模板文件（含 `{{key}}` 占位符）→ `officecli merge` 回填。

**禁止事项**：
1. 禁止在模板中用 Jinja2 语法（`{% for %}`、`{% if %}`）
2. 禁止将 MD 中间层文件作为最终交付物
3. 禁止模板文件与数据文件路径混用

### 6.6 常用命令模板

**完整 batch 实战配方**：见 `references/officecli-batch-templates.md`

最常用命令速查：
```bash
# 创建文档
officecli create output.docx

# 添加段落（正文）
officecli add output.docx /body --type paragraph --prop text="正文内容" --prop font.ea=宋体 --prop font.latin="Times New Roman" --prop size=12pt --prop align=both --prop firstLineChars=200 --prop lineSpacing=1.5

# 批量执行（JSON 文件）
officecli batch output.docx --input batch.json

# 设置页边距（客户版 2.2/2.4cm）
officecli set output.docx /section[1] --prop marginTop=2.2cm --prop marginBottom=2.2cm --prop marginLeft=2.4cm --prop marginRight=2.4cm

# 设置页边距（法院版 3.7/3.5/2.8/2.6cm，红圈所标准）
officecli set output.docx /section[1] --prop marginTop=3.7cm --prop marginBottom=3.5cm --prop marginLeft=2.8cm --prop marginRight=2.6cm

# 保存
officecli save output.docx

# 校验
officecli validate output.docx
officecli view output.docx issues
```

## 7. 禁止清单

### 格式类

1. **禁止表格中使用 ✅❌ 等非文字符号**——统一使用文字表述（"是/否"）
2. **禁止标题层级跳跃**——不得从一级直接跳到三级（如"一、"后直接"1."）；默认两级，扩展最多四级（一、→（一）→1.→（1））
3. **禁止手动敲空行**——Word 中连续两个段落标记 = 排版不合格
4. **禁止英文/数字使用中文字体**——所有 run 的 `w:ascii` 和 `w:hAnsi` 必须为 "Times New Roman"
5. **禁止使用禁用字体**——MS Gothic / MS Mincho / Yu Gothic / Calibri / 等线 / 微软雅黑
6. **禁止中文段落使用直双引号**——必须使用全角双引号（U+201C/U+201D）
7. **禁止法律文书使用感叹号**——陈述事实用句号，并列陈述用分号
8. **禁止中英文标点混用**——中文标点跟随中文字体，西文标点跟随西文字体（TNR）
9. **禁止标题带句号**——各级标题末尾不带句号；"1."后为半角点号，不可用顿号
10. **禁止 C 轨备忘录漏用强调色**——非诉商务文件（Memo/分析报告/服务方案）默认强制藏蓝 #1A3A5C，不得因"客户没要求"而省略
11. **禁止强调色超范围或正文用色**——强调色仅限一级标题/表头/页眉分隔线三类元素，正文 100% 黑色
12. **禁止表头偏离默认样式**——C 轨表头固定浅藏蓝底+藏蓝字；客户明确要求深蓝底白字才启用备选，禁止自行选择

### 工具类

13. **禁止在同一个 task 中混用 OfficeCLI 和 python-docx 修改同一个 docx**——两者解析 OOXML 方式不同，混用导致段落结构错乱
14. **禁止用 OfficeCLI 的 `set --prop font` 替代 `add run --prop font.ea/font.latin`**——set cell/prop 会污染 ascii 字段
15. **禁止 OfficeCLI 修订操作的 author 使用 WorkBuddy/AI 或个人姓名**——统一"律师"（v7.1）
16. **禁止跳过首次最小验证直接生成大批量 batch 指令**——必须先建最小测试文档（≤5 条指令）验证 props 语法
17. **禁止 `set` 命令使用 `firstLine` 属性**——正确属性名是 `firstLineIndent`（长度值，如 `0.85cm`）
18. **禁止 batch 内 props 用 `font` 对象嵌套**——必须点分写法 `font.ea`/`font.latin`
19. **禁止 `add --type field` 时设置 `font.ea`/`font.latin`**——域字段不支持字体 props，须在 add 后用 `set` 单独给结果 run 设字体

### 流程类

20. **禁止用正则跨段模糊匹配做批量格式修正**——必须逐段独立切分后，用双条件（有A无B/有B无A）精确定位目标段落
21. **禁止无备份就覆盖原文件**——任何修订操作前必须备份
22. **禁止在旧式 `.doc` 或 `.wps` 格式上操作**——先另存为 `.docx`
23. **禁止直接修改后加颜色伪装**——颜色高亮不是修订痕迹，不能替代 track changes
24. **禁止把"批注"当"修订"**——批注是评论，修订是修改痕迹，两者功能不同
25. **禁止在已有 `<w:ins>` 内再次生成新修订**——会导致嵌套修订
26. **禁止格式调整不留修订痕迹**——改字体/加粗/颜色/对齐等必须用 format 修订（rPrChange），禁止直接覆盖式改格式（v7.1）
27. **禁止把未修改的整句/整段塞进修订标记**——最小精确编辑，只标记实际变化的文本（v7.1）
28. **禁止未经审查的 Accept All**——接受/拒绝修订必须逐条审查后执行（v7.1）
29. **禁止修订 author 使用个人姓名**——统一"律师"，V 阶段 `query revision[@author!='律师']` 校验（v7.1）

### 交付类

30. **禁止在 WPS 终端之前将 OfficeCLI 产物直接交付客户**——WPS 打开核对为最后一道检查
31. **禁止跳过任何一方双引擎核验**——OfficeCLI validate 通过不代表排版正确，python-docx 字体检查通过也不代表结构无错
32. **禁止将审查脚本的输出作为最终交付物**——审查报告是内部的
33. **禁止将 MD 中间层文件作为最终交付物**——MD 是内部中间产物，正式交付必须走 docx
34. **禁止在模板中用 Jinja2 语法**——OfficeCLI `merge` 只支持 `{{key}}` 占位符替换

## V 阶段防偷懒合约条款（v6.4 强制，2026-08-09）

> **来源**：防偷懒三层防御体系（`项目记忆文件` 唯一权威源）。V0.5 确定性门禁自动检查，不达标 BLOCK。

### 合约 1：审校清单逐项执行（防"跳检查项"）

- **claim**：V 阶段 23 项审校清单逐项核验，不得凭"看起来没问题"跳过
- **verification**：deterministic（审查报告逐项列出 ✅/❌，任一 ❌ 未修正不得进入交付）
- **consequence**：审查报告缺项或"全部通过"但无逐项证据 → BLOCK，标记"跳检查项"

### 合约 2：双引擎核验不可省（防"单引擎交付"）

- **claim**：OfficeCLI validate + 独立核验（OOXML 检查）双引擎，WPS 打开核对为最后一道
- **verification**：deterministic（检查核验记录：validate 输出 + 字体 OOXML 检查 + WPS 打开确认）
- **consequence**：跳过任一核验 → BLOCK，不得交付

### 合约 3：版本与残留合规（防"版本混乱"）

- **claim**：定稿才限制编辑（仅黄色高亮可改）；客户版零内部痕迹；临时文件清理
- **verification**：deterministic（检查文件属性：编辑限制已启用；搜索内部痕迹关键词；检查临时文件）
- **consequence**：客户版含内部痕迹 / 未限制编辑 → BLOCK

### 合约 4：修订模式核验不可省（v7.1 新增，防"改完不留痕"）

- **claim**：含修订的文档，author 全为"律师"；添加/删除/格式调整全类型原生留痕；接受/拒绝双向验证通过
- **verification**：deterministic（`query revision[@author!='律师']` 零命中 + OOXML 检查 w:ins/w:del/w:rPrChange 覆盖全部修改 + 接受/拒绝后内容对比）
- **consequence**：任一修订非"律师"author / 存在未留痕修改 / 双向验证失败 → BLOCK，不得交付

### 反合理化新增条目

| 借口 | 触发场景 | 反驳 | 替代方案 |
|------|---------|------|---------|
| "排版看起来没问题，不用逐项查" | 简单文档 | 23 项清单每项都可能出错（字体/编号/页码/标点/强调色），"看起来没问题"是偷懒信号 | 逐项跑清单，每一项给出核验证据 |
| "这个文档小，不用双引擎核验" | 单页文书 | 双引擎核验是硬规则，与文档大小无关。OfficeCLI validate 通过不代表字体正确 | 至少完成 OfficeCLI validate + 字体 OOXML 检查两项 |
| "客户版检查过了没有内部痕迹" | 客户交付 | 内部痕迹（案件编号/批注/REF）可能在 WPS 打开时才暴露 | WPS 打开核对为最后一道，必须执行 |
