# 对抗式审查

> 对成熟交付物进行多视角、独立 Agent、高判断力模型的对抗式审查。输出审查报告 + 修改方案（按 P0-P3 分级），或审查+直接优化二合一。

## 定位与边界

| 维度 | 说明 |
|------|------|
| **输入** | 一份结构完整、自认为可交付的成熟成果。明显半成品退回让用户先补完，不启动审查 |
| **产出** | 模式A：审查报告 + P0-P3 分级修改方案（硬停等人工确认后执行修改）；模式B：审查 + 直接优化，产出修改后的成品（有 P0 熔断，见下） |
| **与任务执行方法论的关系** | 见下方「体系关系」——任务执行方法论是权威源，本技能只定义独立入口的流程编排 |

### 体系关系（冲突仲裁规则）

1. **使用时机**：任务执行方法论流程内产出的交付物 → 走方法论内嵌验证阶段；用户直接提交的外部/既有成果（非本次方法论流程产出）→ 走本技能。
2. **冲突仲裁**：任务执行方法论是方法论体系权威源。视角定义、Kill Mandate、攻击角度下限、分级标准等参数与本技能不一致时，**以方法论验证阶段为准**。本技能只定义独立入口的流程编排（模式A/B、触发门槛、验证者环节、修改闭环），不重复定义方法论细节。
3. **交付形式审查**：对抗式审查含内容实质 + 交付形式两大维度，缺一不可。本技能的审查要点覆盖内容实质维度；**交付形式审查（排版/去AI味/命名规范）按通用交付标准执行**，本技能不重复——文字类交付物调用写作风格规范，Word 交付物调用文书排版规范，公众号调用公众号写作规范。

## 触发门槛（复杂度自评）

spawn 审查 Agent 之前，主会话先对交付物打分（每项 1 分）：

| 信号 | 分 |
|------|---|
| 法律定稿/客户版/法院版/对外发布（不可逆、高风险） | 1 |
| 涉及金额、权利义务、法律责任判断 | 1 |
| 多章节/多组成部分，一部分出错影响整体 | 1 |
| 篇幅 >2000 字或包含 ≥3 个独立论证模块 | 1 |
| 将被他人（客户/法官/监管/平台）直接依据或评判 | 1 |

- **0-1 分** → 不走本技能，主会话简单检查即可
- **2-3 分** → Light 档（1 个高判断力 Agent 顺序跑 2 视角，视角输出各自独立成文）
- **≥4 分** → Standard 档（≥3 个高判断力 Agent 各跑 1 视角 + 验证者环节）
- **≥4 分且为法律定稿/对外发布** → Brutal 档（Standard + 全票通过时追加不同模型家族复核）

## 两种输出模式

| 模式 | 触发 | 流程 | 产出物 |
|------|------|------|--------|
| **模式A：审查报告 + 修改方案** | 用户说"审一下""出个审查报告""给我修改意见" | 审查 → 输出分级修改方案 → **硬停** → 用户确认 → 执行修改 | ①审查报告（含分级修改方案）②确认后修改后的成品 |
| **模式B：审查 + 直接优化** | 用户明确说"审完直接改""审查并优化""一步到位" | 审查 → 直接执行修改 → 输出成品 + 修改说明 | ①修改后的成品 ②修改说明（改了什么、为什么） |

**模式判定规则**：
- 用户未明确指定 → 默认模式A（审查是重决策环节，人工把关不可省）
- 触发词冲突时（如"审一下，有问题顺手改"同时命中两者）→ 按模式A 处理（安全侧兜底）
- **模式B 的 P0 熔断**：模式B 下审查发现 P0 级发现（含方向性错误）→ 自动升级为模式A 硬停，向用户说明问题后再决定是否修改。方向性问题不自动改

## 核心铁律（不可突破）

### 铁律一：独立 Agent 审查，执行者 ≠ 审查者

审查 Agent 必须是**独立的 Sub-Agent**，与产出该交付物的执行 Agent 不是同一个。主会话不亲自执行审查——主会话只负责分派、把关、汇总。**修改后自检不算审查**——P0/P1 修复后的复审必须由审查视角（或其替代高判断力 Agent）执行，不能由修改者自查。

### 铁律二：≥2 个独立审查视角，通常 3 个

视角数量是质量要求，Agent 数量是实现手段：
- **Light 档**：1 个高判断力 Agent 顺序执行 2 个视角，每个视角的输出必须各自独立成文、互不干扰
- **Standard/Brutal 档**：≥3 个独立高判断力 Agent，每个跑 1 个视角

**裁判视角强制**：审查视角中必须包含 1 个裁判视角（中立第三方；Light 档仅 2 视角时除外，走 fallback：主会话扮演裁判 + 倾向保守选项）。

### 铁律三：审查 Agent 必须是高判断力模型

普通执行型模型没有足够判断力做对抗式审查。所有审查 Agent 和验证 Agent 必须指定高判断力模型。

### 铁律四：角色视角审查，不是泛泛检查

每个审查 Agent 必须被赋予一个**具体的角色身份**（姓名 + 核心关注点 + 攻击方向），从该角色的立场出发攻击交付物。禁止"请检查这份文档有没有问题"式的无角色审查。

### 铁律五：审查深度量化下限（Kill Mandate）

每个审查 Agent 的任务不是"找问题"，是**"试图推翻核心结论"——推不翻才放行**。每个视角的报告必须以"我试图从 X 角度推翻这个结论，因为 Y"开头；写不出"试图推翻但失败"= 审查深度不够，重做。**每视角最少攻击角度数：我方 2 个 / 对方 3 个 / 裁判 2 个**。

### 铁律六：主会话带背景审核义务（分派与验收两环）

分派时，**每个审查 Agent 必须收到项目背景 + 审查目的 + 交付物上下文**，禁止只发角色和任务清单的"裸分派"。验收时，**主会话有义务带着项目背景和审查目的审核每个 Agent 的返回结果**，不得机械转贴。

## 审查流程

```
主会话（接收交付物 → 复杂度自评定档 → 判模式 → 定视角 → 拟要点 → 建分派简报 → 分派 → 验证 → 带背景审核 → 汇总 → 输出）
  │
  ├─ Step 0: 复杂度自评 → 定档（Light/Standard/Brutal）
  ├─ Step 1: 识别交付物类型 + 判定输出模式（A/B）
  ├─ Step 2: 选定审查视角 + 为每个视角定义角色身份
  ├─ Step 3: 为每个视角草拟审查要点（结合交付物特点，补充用户没想到的）
  ├─ Step 3.5: 构建分派简报——项目背景 + 审查目的 + 交付物上下文 + 角色/要点 + 边界行
  ├─ Step 4: spawn 独立高判断力审查 Agent，每个带完整分派简报
  ├─ Step 4.5: 验证者环节——spawn 1 个高判断力验证 Agent，对每条 P0/P1 候选发现逐条反驳
  ├─ Step 5: 带背景审核（目的相关性/事实符合性/边界合规/遗漏判断）→ 汇总 → 去重合并 → P0-P3 分级 → 聚合判定
  │
  ├─ 模式A: 输出审查报告 + 分级修改方案 →【硬停：用户确认】→ 执行修改 → P0/P1 修复复审 → 输出成品
  └─ 模式B: P0 熔断检查 → 直接执行修改 → P0/P1 修复复审 → 输出成品 + 修改说明
```

### Step 1: 识别交付物类型 + 判定输出模式

识别交付物类型，判定模式A/B（判定规则见上）。

### Step 2: 选定审查视角 + 定义角色身份

**视角选择原则**：根据交付物类型，从视角池中选取（含 1 个裁判视角）。用户指定了视角 → 用用户的；用户未指定 → 主会话自行评估并安排。

**视角池**（按交付物类型映射，示例非穷举——主会话可自定义）：

| 交付物类型 | 我方视角 | 对方视角 | 裁判视角 | 可选补充视角 |
|-----------|---------|---------|---------|------------|
| 起诉状/答辩状/代理词/上诉状 | 经办律师——请求权基础完整性、证据链闭合度 | 对方律师——逻辑漏洞、法条过时、证据不足、程序瑕疵 | 承办法官——要件满足、说理充分、判决可执行性 | 审委会专家——类案一致性 |
| 诉讼策略报告 | 执行律师——策略可行性、风险评估完整性 | 对方律师——策略漏洞、我方弱点暴露 | 资深合伙人——商业合理性、客户期望管理 | 行业专家——技术/行业准确性 |
| 证据分析报告 | 证据律师——三性、证据链闭合度、确信度分级 | 对方律师——证据真实性、关联性、来源可靠性 | 法官——证据可采信性、证明力充分性 | 鉴定专家——技术真实性 |
| 法律检索报告 | 检索律师——检索策略全面性、来源权威性 | 假设对方律师——遗漏的反面案例、过时法条 | 审委会专家——检索质量、法源覆盖完整性 | — |
| 合同 | 起草律师——条款公平性、风险分配合理性 | 对方公司法务——对我方不利条款、修改建议合理性 | 仲裁员——条款可执行性、争议解决条款有效性 | 行业专家——行业惯例符合度 |
| 法律意见书/律师函 | 经办律师——分析深度、法条引用准确性 | 对方法务——不利解读可能性 | 客户法务总监——商业价值、可执行性 | 监管专家——合规风险 |
| 公众号文章 | 作者——事实准确性、法律引用有据 | 平台审核员——违规风险、不良信息、导流嫌疑 | 同行律师——专业度、法律错误、可读性 | 普通读者——看得懂、读得下去 |
| 尽调报告 | 执行律师——完整性、格式合规、数据来源 | 监管审核员——合规缺陷、数据不实 | 行业专家——可行性、市场分析合理性 | 客户——需求覆盖、商业价值 |
| 可研报告 | 编制人——数据准确性、逻辑完整性 | 审批机关——合规性、风险分析充分性 | 行业专家——技术路线可行性 | 财务专家——财务模型合理性 |
| 方案/备忘录 | 起草人——逻辑完整性、方案可行性 | 目标读者/决策者的反对者——挑刺、找漏洞 | 有公信力的中立第三方——客观评判 | 执行落地人——可操作性 |
| 数据类交付物（Excel/台账） | 编制人——数据准确性、计算逻辑 | 审计员——数据造假、计算错误、口径不一致 | 财务/数据专家——分析方法正确性 | 使用方——可用性 |
| 代码/技术方案 | 开发者——功能正确性、边界条件 | 安全审计员——安全漏洞、注入风险 | 架构师——架构合理性、可维护性 | 运维——部署可行性、回滚方案 |

**角色身份定义三要素**（每个视角必须定义）：
1. **姓名**：虚构但合理（如"张律师""李法官""王法务"）
2. **核心关注点**：这个角色最在意什么（1-2句话）
3. **攻击方向**：这个角色会从哪里挑刺（满足铁律五的数量下限）

### Step 3: 草拟审查要点

**通用审查要点**（所有交付物必查，内容实质维度）：

| 维度 | 审查内容 |
|------|---------|
| 事实准确性 | 事实/数据/日期/金额/主体名称是否有据可查，与原始材料一致 |
| 逻辑完整性 | 论证链是否有跳跃，因果是否成立，前提是否隐含假设 |
| 来源可靠性 | 引用来源是否权威、是否 ≥2 独立来源、是否标注确信度 |
| 法条/规则时效 | 引用法条是否现行有效，是否有更新/废止/修正 |
| 反面信息 | 是否存在被忽略的不利证据/反面案例/反对意见 |
| 边界条件 | 是否考虑了极端情况、例外情形、边界条件 |
| 可执行性 | 结论/建议是否可操作，是否有落地路径 |
| 语言表达 | 无AI味、无废话、逻辑连贯、专业语气 |

**视角专属审查要点**：根据 Step 2 选定的视角，为每个视角补充该角色独有的关注点。

**主会话补充要点**：主会话必须根据交付物的具体内容，补充用户和视角池都没想到的审查要点。这是主会话的核心价值——**想到用户没想到的**。

### Step 3.5: 构建分派简报（项目背景 + 审查目的 + 边界）

spawn 之前，主会话必须为每个审查 Agent 构建一份**结构化分派简报**（五要素）。审查 Agent 的场景化五要素：

| 要素 | 本技能映射 | 反例 |
|------|-----------|------|
| **① 项目背景** | 这是什么案件/项目？给谁看的？现状如何？1-3 句浓缩 | 只给文件名 |
| **② 审查目的** | 这次审查要达成什么？（如"判断起诉状能否立案""评估公众号文章是否踩平台红线"） | 不写目的，默认"找毛病" |
| **③ 交付物上下文** | 交付物的性质、用途、读者、已定事实/口径、已知约束 | 只贴全文让 Agent 自己猜 |
| **④ 角色与要点** | Step 2 角色身份 + Step 3 审查要点（对应通用要素④"指令与产出契约"） | — |
| **⑤ 边界行** | 只审不改（审查 Agent 不参与修改）、不新增审查视角、不重写交付物、发现以 P0-P3 分级 | 无边界行，Agent 自由发挥 |

**传递规则**：传结构化状态而非完整历史——背景/目的/上下文用精炼段落，交付物全文附上，但不传用户原对话记录和其他审查 Agent 的中间输出（防级联污染和角色混淆）。

### Step 4: spawn 独立审查 Agent（携带完整分派简报）

**工具调用**：spawn 独立 Sub-Agent，指定高判断力模型。Standard/Brutal 档并行 spawn（互不依赖），每个 Agent 独立输出，互不可见。

**每个审查 Agent 的 prompt 结构**（必须含分派简报五要素，禁止"裸分派"）：
```
【项目背景】[① 1-3 句浓缩背景]
【审查目的】[② 这次审查要达成什么]
【交付物上下文】[③ 交付物性质/用途/读者/已定口径/已知约束]
交付物全文：[附上，或给出文件路径]

【你的角色】你是[角色姓名]，[角色身份描述]。
你的核心关注点：[1-2句话]。
你的攻击方向：[满足铁律五数量下限的具体攻击点]。

你的任务：对上述交付物进行对抗式审查。不是"找问题"，是"试图推翻这份交付物的核心结论"——推不翻才放行。

【审查要点】[通用要点 + 视角专属要点 + 主会话补充要点]

【边界行】只审查不修改；不新增本简报外的审查视角；不重写交付物；发现以 P0-P3 分级输出。

【输出格式】：
1. 角色声明：我是谁，我从什么角度审查
2. 攻击记录：每个攻击角度（攻击方法/结果[推翻成功/推不翻]/证据）
3. 发现清单：每条含 STATUS: 候选 + 分级（P0致命/P1严重/P2改进/P3可选）+ 问题描述/位置/修改建议
4. 总体判定：PASS / BLOCK
5. 最没把握的3件事（不确定性自曝）
```

### Step 4.5: 验证者环节（发现反驳闸门）

审查 Agent 的发现不能直达用户——高判断力模型也会幻觉式挑刺。spawn 1 个独立高判断力验证 Agent（≠所有审查 Agent），对每条 P0/P1 候选发现**逐条反驳**（不是打包确认——打包会稀释审查解析度）：

- **反驳成功** → 该发现标 `STATUS: REBUTTED`，不进入报告正文，写入附录备查（含反驳理由）
- **反驳失败** → 该发现标 `STATUS: CONFIRMED`，进入报告正文
- P2/P3 发现可抽查反驳，不必逐条

**Light 档降级**：验证者环节由主会话逐条反驳执行（不 spawn 额外 Agent）。

**全票通过警惕（unanimity-as-warning）**：Brutal 档所有审查视角一致 PASS 时，追加 1 个不同模型家族的高判断力 Agent 复核，仍为 PASS 才放行。

### Step 5: 带背景审核 → 汇总 → 分级 → 聚合判定

**第一步·带背景审核（主会话义务，铁律六）**：收到每个审查 Agent 的返回结果后，主会话必须先带着分派简报中的项目背景和审查目的审核结果，**不得机械转贴**。四问审核：

| 审核问 | 检查什么 | 不通过处理 |
|--------|---------|-----------|
| ① 目的相关性 | 发现是否服务于审查目的？还是 Agent 自创视角的跑题发现？ | 与目的无关的发现降级或剔除，并记录 |
| ② 事实符合性 | 发现中的事实/假设是否与项目背景、已定口径冲突？（防级联污染——Agent 对背景的错误假设） | 冲突发现打回该 Agent 澄清或剔除 |
| ③ 边界合规 | 是否越界（改了交付物/重写了/新增视角）？输出格式是否契约合规？ | 越界部分作废，要求按边界行重出 |
| ④ 遗漏判断 | 对照审查要点，Agent 是否漏审了与项目目的最相关的点？ | 漏审点由主会话补充追问或补审 |

**第二步·汇总**（审核通过后）：收集所有 CONFIRMED 发现，执行：
1. **去重合并**：多个视角发现的同一问题合并为一条
2. **冲突仲裁**：不同视角意见冲突时，按裁判视角优先；无裁判视角时（仅 Light 档允许）主会话扮演裁判 + 倾向保守选项
3. **分级排序**（统一使用 P0-P3 四级，全链路一致）：

| 分级 | 定义 | 处理 |
|------|------|------|
| **P0 致命** | 不修复就不能交付（事实错误/法条过时/逻辑断裂/方向性错误） | 必须修复 |
| **P1 严重** | 影响质量但不影响方向（论据不足/反面信息遗漏/表达不当） | 强烈建议修复 |
| **P2 改进** | 可以更好（措辞优化/结构微调/补充说明） | 建议修复 |
| **P3 可选** | 锦上添花（风格偏好/排版细节） | 可选 |

4. **聚合判定规则**（机器可执行；视角判定以 Step 4.5 反驳后的 CONFIRMED 发现重新核定，被 REBUTTED 的发现不再支撑该视角的 BLOCK）：
   - 任一视角总体判定 BLOCK（基于 CONFIRMED 发现）→ 总体 BLOCK
   - 任一 CONFIRMED 发现为 P0 → 总体 BLOCK
   - 其余 → PASS

### 模式A：硬停确认

输出审查报告（含分级修改方案）→ **硬停** → 用户确认"可以/确认/执行"→ 执行修改 → P0/P1 修复复审 → 输出成品 + 修改说明。

用户提修改意见 → 修订方案 → 再确认（最多 2 轮，第 3 轮说明方向问题需重新审视）。

### 模式B：直接修改（含 P0 熔断）

审查完成 → **P0 熔断检查**（有 P0 → 升级模式A 硬停）→ 直接执行修改 → P0/P1 修复复审 → 输出成品 + 修改说明（改了什么、为什么、原文是什么）。

### 修改与复审闭环

**修改执行主体**：由主会话直接执行或重新分派 Worker Agent 执行；**审查 Agent 不参与修改**（保持审修分离）。

**修改纪律**：
- 修改前备份原始文件（多轮审查场景用 `_review_v1/`、`_review_v2/` 目录隔离基线，不覆盖历史版本）
- 保持格式（读取→保持→写入）
- 只改审查发现的问题，不做无关重构

**修复复审（强制，非可选）**：
- P0/P1 修复后，必须由至少 1 个原审查视角（或其替代高判断力 Agent）对修改点做**针对性复审**（只审修改点，不重新全审），复审 PASS 才交付
- 复审发现修改引入新 P0/P1 问题 → 触发完整二轮审查
- P2/P3 修复后主会话自检即可

## 与其他技能的关系

| 技能 | 关系 |
|------|------|
| 任务执行方法论 | **权威源**。其验证阶段内嵌对抗式审查；本技能是独立入口。参数冲突以方法论为准 |
| 交付形式审查 | 排版/去AI味/命名规范按通用交付标准执行，本技能不重复 |
| 写作风格规范 | 文字类交付物形式审查调用 |
| 文书排版规范 | Word 交付物形式审查调用 |

## 失败模式防御

| 失败模式 | 表现 | 防御 |
|---------|------|------|
| 审查流于形式 | "整体不错，建议优化措辞"式的空话 | 铁律五 Kill Mandate + 攻击角度量化下限（2/3/2），写不出"试图推翻但失败"=重做 |
| 假阳性直达用户 | 审查 Agent 幻觉式挑刺，用户被误导 | Step 4.5 验证者逐条反驳，REBUTTED 写入附录 |
| 视角同质化 | 三个视角说一样的话 | 角色身份必须具体（姓名+关注点+攻击方向），禁止泛泛的"对方视角" |
| 用户视角遗漏 | 用户没说的视角没想到 | 主会话必须主动评估并补充视角，不能只用用户指定的 |
| 审查要点不全 | 只查了用户提到的点 | 主会话必须补充用户没想到的审查要点 |
| 修改引入新问题 | 修了A问题引入B问题 | 修改与复审闭环：P0/P1 强制针对性复审，新 P0/P1 触发完整二轮 |
| 修改者自查代替复审 | 执行者改完自己说"没问题" | 铁律一：修改后自检不算审查，复审必须由审查视角执行 |
| 方向错误被直接改 | 模式B 下 P0 方向问题被自动改完交付 | 模式B P0 熔断：自动升级模式A 硬停 |
| 全票通过警惕 | 所有审查者一致同意 | unanimity-as-warning：Brutal 档追加不同模型家族高判断力 Agent 复核 |
| 裸分派 | 分派 prompt 只有角色+任务，无项目背景/目的，审查 Agent 凭错误假设产出跑题发现 | Step 3.5 分派简报五要素强制（背景/目的/上下文/角色要点/边界行），缺任一要素不得 spawn |
| 机械转贴汇总 | 主会话不审结果直接转贴，sub Agent 的假设性发现被当事实写进报告 | Step 5 带背景审核四问（目的相关性/事实符合性/边界合规/遗漏判断），不通过不得进入汇总 |
| 级联污染 | 前序 Agent 的错误假设被后续环节当 ground truth 放大 | 分派简报不传其他 Agent 中间输出；Step 5 ②事实符合性检查兜底 |
